**研究目标与约束：**

- 插件不改，优化插件之下的核心机制；不能把插件业务改成C来代替这一目标。
- 场景使用的路由、上下文、阶段调度、配置/身份合并、SDK、上游和清理等核心责任由C承担。
  必要的Lua协程传输与对象适配可以保留，不能用旧Lua核心完成实际核心决策。
- standalone HTTP，实际代理。最初场景为全局Prometheus、前缀路由key-auth/limit-count；
  后来还有全局Prometheus+limit-count和仅limit-count的独立场景。每次比较明确启用列表、
  全局/路由布局和版本；双方排除AI，不混用不同场景的数字。
- 健康检查、慢启动、服务发现和其他范围外功能无需补齐，保留骨架/文档即可。
- 保留插件可观察的顺序、nil/false、yield、getter/cache时机、元数据、共享配额、
  重试/keepalive、错误处理及请求/配置代际生命周期；不同设计的兼容边界要明确。
- 正式压力样本60秒，通常预热5秒；同硬件、依赖、配置和原版Lua对照，报告错误、
  QPS、CPU/请求、内存和Latency。先验证正确性，再测正常构建；保留负结果和版本身份。

**不要预先继承的结论：**

- 用户相信C模型存在CPU/内存优化空间，把早期极简约40%–50%的提升作为重要参考；
  不要把它直接当完整实现的已证明上限，也不要预设当前实现已经到顶。
- 用户未接受最后的纯核心归因解释。scope探针有JIT扰动，减法有基线漂移，
