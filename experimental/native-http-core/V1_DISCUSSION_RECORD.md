## 用户提出、值得保留的技术思路

### H01：C实现的性能空间

用户认为，从CPU和内存效率看C模型应更优，认为改为C后性能更差不符合其预期；
并指出早期极简实现约40%–50%的提升，“大概率是我们能够优化到的一个天花板”。
这是用户的重要研究判断与动机，应完整传递，不能改写成用户接受了当前收益已到极限。

V1同时保留事实边界：早期原型未覆盖后来完整核心责任；C/Lua跨界、对象适配、JIT和GC仍会影响整体成本。
其数字不是完整实现的已证明上限，也不意味着当前实现没有继续优化的空间。

### H02：穿透到已有底层API

用户以 `upstream_response_time` 为例，建议直接查看第三方库具体实现和公开API；
“我也不介意在这里面直接用 if else 的方式读取 nginx 变量”。
这是明确提出的优化方向。V1已经采用typed runtime C API、NGINX变量API及直接header/upstream原语，
后续应先核对已实现部分，继续寻找多余中转，而非重复提出相同优化。

### H03：把整体成本拆开看

用户要求独立比较被改造核心的消耗、额外GC与Latency影响，排除NGINX上下游及插件业务时间。
用户把成本分为NGINX、插件和中间APISIX模块三块，并质疑较窄的scope计时不能覆盖真正被改造的全部机制成本。
用户估计核心可能占整体约30%–40%量级；这是用于质疑计量覆盖面的估计，不是已测出的占比。

### H04：减法与工作量放大

用户提出纯NGINX反向代理与APISIX代理对照，并通过让插件强制执行多次、插值/减法估计开销。
先要求“先想一想……不用做”，之后明确回复“OK，你试试吧”，授权执行了这一测量实验。
这允许实验性的临时插件副本修改，不改变U01所约束的正常插件业务实现。

该思路及执行记录均留档。授权尝试不等于认可实验最后的归因：
用户最新明确表示“你最后这个结论好像跟我想的不太一样”。因此不能写成用户已接受
纯核心18.43%、重复路径34.18%或此前插桩约20%等数字为最终结论。

## 助手认为需要继续保留的重要认识

下列是实现与实验的归纳，**不标为用户逐项认可**。

1. **核心所有权要能核验。** 原版Lua核心加载守卫、C路由/状态机/合并/上游/清理及差分检查，
   比仅说“入口换成C”更能说明改造范围。ABI适配和Lua运行时仍有真实成本。
2. **减少跨界和重复工作优先于语言标签。** 去掉pack临时表、配置/计划缓存、直接runtime API、
   C过滤链、延后JSON、变量批量准备等已经尝试；首次完整C版本出现过明显负收益，过程与修复不能丢掉。
3. **已试与已采用分开。** 后续16项候选、O3/LTO变体、共享正确性修复、负收益和未入选组合均保留。
   当前源码保留开关不代表全部默认启用，也不证明每项独立有收益。
4. **语义是约束。** nil/false、yield、可变getter、插件元数据、共享配额、重试/keepalive、
   请求池与配置代际生命周期不能为了快而静默改变；已知URI策略、池别名与SDK热替换边界必须显式说明。
5. **测试场景与版本必须绑定。** 历史v6、稳定源候选和诊断构建有不同的源文件/模块/运行时身份。
   约12%的历史限流复测、后续候选6.81%的单插件结果以及诊断数字不能跨版本拼接。
6. **整体CPU、纯核心与延迟不是一个指标。** worker CPU包含NGINX/VM/GC；scope可能漏入口退出；
   探针会改变JIT；p99不能做部件相减。GC已计入CPU时不能再重复加上。
7. **减法仍需控制漂移。** 本轮基线漂移明显，k又随时间递增；较高R²不能独立证明斜率差的因果来源。
   同请求重复执行可命中缓存，不能等同于多个独立请求。改进方法是后续假设，不应拿更好样本覆盖本轮。
8. **预研保留未知。** 当前没有可靠的纯核心净倍率、核心因果GC分摊或最终架构结论；
   一分钟压力与模块ASan/UBSan也不构成长期稳定性/全插件兼容证明。
